Yama / Google Play / Checked 3 November 2026

Get Yama onto your phone.
Then invite your friends.

Work through one step at a time. Each step says where to go, what to enter, and what you should see before moving on. You can stop between steps and return later.

The goal: a free Android app on Google Play's closed testing track, available to the friends you choose.

The app code, power-user restrictions, and account-deletion feature are merged. This guide covers the remaining setup and verification; it does not mean the app has already been published or that real-device Google sign-in has passed.

You will use three places: Google Cloud for sign-in, GitHub for builds, and Play Console for distribution. They are separate websites.

One product choice before submission

The current Android build includes the full app, including online Play. Ordinary users cannot use Ask Claude, which an admin grants with power-user access. Every account can watch the computer play (10 games a day) and start one short simulation a day; larger simulations also need power-user access.

You can follow the setup with this build. Before submitting it, decide whether you want to keep the full app or ask the coding agent for a companion-only build. There is currently no Console switch that removes online Play. A companion-only build needs a code change and a new bundle. Do not advertise native ML Kit scanning as shipped; that is future work.

Step 2 of 12 / Google Cloud

Tell Google about the debug app

This lets the test APK built by GitHub use Google sign-in. An OAuth client is Google's registration for this particular app and signing certificate.

  1. In Google Auth Platform → Clients, confirm the selected project is yama-512101. Older menus may put this under APIs & Services → Credentials.
  2. Leave the existing Web application client alone. The server and app already use its ID.
  3. Look for an Android client with the package and fingerprint below. If it exists, reuse it. Otherwise click Create client, then select Android.

Step 3 of 12 / Your Mac and 1Password

Create and save your upload key

The upload key signs the file you send to Google. Google later signs the app people install with a different key. Keep your upload key for future updates.

  1. Open Terminal on your Mac (Spotlight → type “Terminal” → Return).
  2. Paste the following block and press Return. This saves the key outside every Git repository. If a key already exists, the command says so and leaves it alone; use the saved key and its known passwords.
umask 077
mkdir -p "$HOME/.config/yama/android"
chmod 700 "$HOME/.config/yama/android"
if [ -e "$HOME/.config/yama/android/yama-upload.jks" ]; then
  printf 'An upload key already exists. Reuse it and its saved passwords.\n'
else
  /opt/homebrew/opt/openjdk@21/bin/keytool -genkeypair \
    -storetype JKS \
    -keystore "$HOME/.config/yama/android/yama-upload.jks" \
    -alias upload -keyalg RSA -keysize 2048 -validity 10950
fi
if [ -f "$HOME/.config/yama/android/yama-upload.jks" ]; then
  chmod 600 "$HOME/.config/yama/android/yama-upload.jks"
fi
  1. When asked for a keystore password, generate and save a strong password in 1Password. Terminal hides password typing; that is normal.
  2. Answer the certificate identity questions with your personal details. Do not use your work email. Confirm the details when asked. At the separate key-password prompt, press Return to reuse the keystore password.
  3. In 1Password, save an item named Yama Android upload signing. Attach yama-upload.jks from ~/.config/yama/android/; Finder → Go → Go to Folder can open that path. Save the alias upload, keystore password, and key password in the same item.

If “No such file or directory” names keytool: JDK 21 is missing from the expected Homebrew location. Ask the coding agent to locate or install JDK 21. You do not need to install Android Studio or the Android SDK to make this key.

If you already had a key but lost its passwords: stop here and recover the saved item. Do not overwrite an existing signing key.

Google's explanation of upload keys and Play App Signing.

Done when: the key exists locally and a recoverable copy, alias, and both passwords are in 1Password. Do not put any of these in this guide, a commit, a screenshot, or chat.

Step 4 of 12 / GitHub

Give GitHub the four signing secrets

  1. Open Yama → Settings → Secrets and variables → Actions.
  2. Under Repository secrets, use New repository secret. These are secrets, not repository variables or environment secrets.
  3. Add each of the four names below exactly. If a secret already exists, update it only with the matching saved key's value.
Secret nameWhat goes in it
ANDROID_UPLOAD_KEYSTORE_BASE64The encoded keystore copied by the command below.
ANDROID_UPLOAD_KEYSTORE_PASSWORDYour keystore password from 1Password.
ANDROID_UPLOAD_KEY_ALIASupload, if you created the key in step 3.
ANDROID_UPLOAD_KEY_PASSWORDYour key password. Same as the keystore password if you pressed Return at that prompt.

For the first secret, run this in Terminal. It copies the encoded key to your clipboard without printing it:

base64 -i "$HOME/.config/yama/android/yama-upload.jks" | pbcopy

Then paste into the Secret field for ANDROID_UPLOAD_KEYSTORE_BASE64 and save. Afterward you can clear the clipboard with printf '' | pbcopy. Paste passwords only into GitHub's secret fields; never put them in a shell command.

Done when: GitHub lists all four repository-secret names. GitHub will not show their saved values again; that is expected.

Step 5 of 12 / GitHub Actions

Build the APK and Play bundle

This is one manual Android build on GitHub-hosted runners, free for the public repository. The Android workflow permits a manual run whether CI tests are on or off.

  1. Open Yama → Actions → Android.
  2. Click Run workflow, select branch main, then confirm Run workflow.
  3. Open the new run. The job is named Build the Android app. The running job has a 30-minute timeout; time sitting in GitHub's queue is separate.
  4. If it fails, open the first failed step. A build-password error means check the four secrets; an Actions billing error means resolve the account limit or ask the agent to build locally under the disk/compiler rules. Do not enable unrelated CI or repeatedly retry the same failure.
  5. When it succeeds, open Signing certificates (for the Android OAuth clients). Check that the release variant has a real signing configuration and SHA-1. If the log says “No upload key in secrets: the release bundle stays unsigned”, the green build is not ready for Play. Fix the secrets and start a new run.
  6. On the run's summary page, scroll to Artifacts and download yama-android-N, where N is the run number. Unzip it.
app-debug.apk
Install this on your own phone for step 6. It uses the debug certificate from step 2.
app-release.aab
Upload this to Play Console in step 8. An AAB cannot be installed by tapping it on a phone.

Keep the run URL and bundle together. Artifacts expire after 14 days. Each fresh workflow run gets a new version code; start a new run for a new Play upload instead of rerunning an old run. Play requires increasing version codes.

About the third certificate: the upload SHA-1 printed here is not Play's app-signing SHA-1. You only need an additional “Yama Android — upload” OAuth client if you later install a release APK signed directly with this upload key. The current workflow emits a debug APK and an AAB, so that extra client is optional for this walkthrough.

Done when: you have a successful run, a signed release bundle, and the debug APK downloaded.

Step 6 of 12 / Your Android phone

Try Google sign-in on your phone

  1. Transfer app-debug.apk to your phone using a USB cable or your own private file transfer. Open it in Files or Downloads.
  2. If Android asks, allow that file-opening app to install unknown apps, then install Yama. You can revoke that permission afterward.
  3. Open Yama. Confirm the life counter and navigation appear.
  4. Tap Sign in → Sign in with Google, pick your Google account, and complete sign-in.
  5. Open a private page, such as your Decks or Collection. Seeing your own data is the proof of sign-in; just seeing Google's account picker is not enough.

If sign-in fails

  • Account picker opens, then errors: check step 2's project, package, and debug SHA-1. Cloud changes can take time to propagate; allow a few minutes before testing again.
  • Google says access is blocked or restricted: check Google Auth Platform → Audience. If the OAuth project is in testing and Google restricts access, add your tester account there. This list is separate from Play's testers. Do not change scopes or the existing Web client to guess at a fix.
  • No data loads: open yama.ing in the phone browser. If the website works but the app does not, give the agent the exact error and build-run URL.
  • “App not installed” / signature conflict: another Yama install may use a different signing key. Sync anything you want to keep before uninstalling it; uninstalling removes its local app data.
Done when: you have signed into the installed APK on a real phone and opened your private data successfully.

Step 7 of 12 / Play Console

Create Yama in Play Console

  1. Open Play Console. If Yama already exists, open it instead of creating another app.
  2. Otherwise click Create app. Enter name Yama, choose your default language, select App for the current companion/tracking listing, and choose Free. If you decide to market the full game client, revisit its category and disclosures before submission.
  3. Read and complete Google's declarations, then click Create app. Complete any developer identity, contact, or device-verification tasks the Console shows for your account.
  4. In the app Dashboard, note any production-access testing requirement. Your account's age has not been verified here. Google's 12-testers-for-14-days rule applies to personal accounts created after 13 November 2023; use what the Console says for this account.

Choosing “Free” is intentional: Yama is free. The package ing.yama.app comes from the uploaded bundle and identifies this app permanently on Play.

Google's account-specific testing requirements. Closed testing is still the plan even if your older account has no production-access gate.

Done when: you are inside Yama's Play Console dashboard and know which account-verification or testing tasks it requires.

Step 8 of 12 / Play Console

Upload the bundle and let Google sign it

  1. Go to Test and release → Testing → Closed testing. Use or create the first closed track; call it Friends beta if a track name is requested.
  2. Click Create new release. Follow the Play App Signing setup. For this new app, let Google generate and protect the app-signing key.
  3. Upload app-release.aab from step 5. Let Play finish processing it. Confirm the package is ing.yama.app and check for signing or target-API errors. The repository currently targets API 36.
  4. Give it a release name such as First friends beta and release notes such as “First closed test of Yama on Android. Please try sign-in, collection, decks, scanning and the life counter.”
  5. Save the draft. Complete steps 9 and 10 before submitting or rolling it out. If Console asks for unfinished app details first, complete those in step 10, then return here.

If Play refuses the file

  • Unsigned: fix step 4's secrets and start a fresh Android workflow run.
  • Version code already used: start a fresh workflow run, download its new AAB, and upload that file.
  • Wrong upload certificate: find the key already registered for this Play app. Do not generate replacement keys at random; an existing app may require an upload-key reset.

A successful server deploy does not publish an Android release. Uploading a draft also does not distribute it. Signing documentation and target API requirements.

Done when: Play has accepted the signed AAB into a saved draft and Play App Signing is configured.

Step 9 of 12 / Play Console, then Google Cloud

Register Google's Play signing certificate

This is the step that makes Google sign-in work for people who install from Play. A working debug APK does not prove the Play-installed app can sign in.

  1. In Play Console, open Test and release → Setup → App integrity (some Console layouts place App integrity directly under Test and release). Open its App signing section.
  2. Find App signing key certificate. Copy its SHA-1 certificate fingerprint. Do not copy the nearby Upload key certificate fingerprint.
  3. Return to Google Auth Platform → Clients in the same Yama project used in step 2.
  4. Create another Android client: name Yama Android — Play, package ing.yama.app, SHA-1 equal to the app-signing fingerprint you just copied. If it already exists with that exact pair, reuse it.
  5. Keep the debug client as well. These registrations can coexist. This change does not require rebuilding the AAB or replacing the existing Web client.

Step 10 of 12 / Play Console

Complete the listing and app-content forms

Follow the remaining setup tasks in Yama's Dashboard. Console labels move; the page names below are the useful things to look for.

Store listing and contact details

  1. Open Grow users → Store presence → Main store listing. Use app name Yama and short description Track Commander games, life totals, decks and your Magic card collection.
  2. For the full description, explain the tracking features, Google sign-in, and the friends beta. Include: “Unofficial fan software. Not affiliated with, endorsed by, or sponsored by Wizards of the Coast.” Describe only features in the uploaded build; Ask Claude and full-size simulations are restricted to approved power users; every account gets one short simulation a day.
  3. Upload a 512 × 512 PNG icon, a 1024 × 500 feature graphic, and at least two actual phone screenshots. Follow the Console's dimension checks. Use screens and original artwork you can distribute; the project rule is no Wizards logos or card images in the listing. Take screenshots with private account information hidden and card-art backgrounds turned off.
  4. In Store settings, set support email bryanroscoe@gmail.com and website https://yama.ing. Choose the category and tags that accurately describe the build.

Official asset requirements. Assets are not generated by this guide; prepare the missing icon/feature graphic/screenshots before submission.

App content

Open Policy and programs → App content (or its Dashboard tasks), then work through each required declaration:

  • Privacy policy: enter https://yama.ing/privacy/. Open it and the deletion page on your phone to check both load.
  • Ads: the current app has no advertising; confirm this still matches the uploaded build.
  • App access: some features require Google sign-in. Explain how a reviewer signs in with their own verified Google account; ordinary accounts need no invitation. State that Ask Claude and full-size simulations are intentionally role-restricted. Use the Console's instructions to supply any further reviewer access it requires. Do not claim the whole app works without sign-in or give away your personal Google credentials. If Google requires access to restricted features, ask the agent to arrange a review path before submitting.
  • Content rating: answer the questionnaire for what is actually included, including online interactions and the game client if kept. Let the questionnaire determine the rating.
  • Target audience: choose the ages you actually intend to serve. The current privacy policy says the app is not intended for children under 13. Do not choose children's audiences as a way to fill a blank; reconcile any conflicting choices with the policy first.
  • Other Dashboard declarations: complete any account-specific or category-specific tasks shown. Read each one rather than selecting “No” across the board.

Step 11 of 12 / Play Console

Choose testers and release the closed test

  1. Return to Test and release → Testing → Closed testing and open your Friends beta track.
  2. On its Testers tab, create an email list with your own Google-account email first. Add the Google-account emails of the friends you want to invite, or choose a Google Group you control. Save.
  3. Select the countries/regions where your testers live. Check the track's availability settings, not just the email list.
  4. Open the saved release. Review the bundle, notes, and Console errors. Fix blocking errors; then use the Console's Review release, Send for review, or Start rollout to closed testing actions as shown.
  5. Check Publishing overview. If managed publishing is enabled, approval can still require a separate Publish changes action. Wait for the release to become available, not merely saved or sent for review.
  6. Copy the track's opt-in link from the Testers page. First open it yourself using the same Google account you added. Join the test, then follow the link to install from Google Play.
  7. Once your own Play install passes step 12, send friends the opt-in link. Tell them which Google account must open it, and ask them to join the test before installing.

If the link says the app is unavailable, check tester email, opt-in status, selected countries, and release availability. First-time test links may take several hours to become available. Approval is not instant.

Switching from the debug APK: Play's signing certificate differs, so Android may require uninstalling the debug app. Sync saved work first. Uninstalling deletes the app's local data. Then install from the regular closed-testing Play link.

Google's testing-track instructions. Closed testing limits distribution; it does not automatically make someone a Yama power user.

Done when: the closed release is available and you have installed it from Google Play using an eligible, opted-in account.

Step 12 of 12 / Your phone and Yama

Verify the Play install and record the handoff

Use the app installed from Google Play, not the debug APK or the website.

  1. Google sign-in: sign in and open your private Collection or Decks. If debug sign-in worked but this fails, recheck step 9's Play app-signing SHA-1.
  2. Ordinary-account restrictions: use a non-admin, non-power-user account to confirm Ask Claude is unavailable, that Try a change offers only a 20-game run and says the account's one short simulation a day, and that a second run the same day is refused with that limit. Existing results should remain readable where authorized. Do not grant every tester power-user access; if desired, grant specific friends in Admin → People.
  3. Phone features: try camera scanning, Android Back, one deck/collection export through the share sheet, and opening the privacy link in the browser. After the app has loaded, try the life counter offline, then reconnect and verify saved changes sync.
  4. Deletion: use only a disposable, non-admin test account with no data you need. Check Your profile → Account settings → Delete account, confirm that account's email, and verify its old session loses access. Do not run this test on your main account. The website's /delete-account/ instructions must also work without the Android app.
  5. Record the release: put the build-run URL, version code, closed-track name, test opt-in link, date, and test results into a private release note or the PR. Certificate fingerprints are public; keep signing keys and passwords in 1Password and the local credential folder.
The friends beta is ready when: a Play-installed copy can sign in, the checks above pass, and invited testers can join through the saved link. A green build, successful upload, or healthy website alone does not prove that.

Later: going beyond the friends beta

Keep the closed test running while you gather feedback. If the account has the newer-personal-account gate, meet the Console's 12-testers/14-continuous-days requirement and apply for production access. Production or open testing is a separate release decision; finishing this guide does not publish to everyone.

If an agent or build gets stuck

The Android build job already has a 30-minute running limit. If a job stays queued for 10 minutes, inspect Actions capacity/billing before starting more jobs. Google review and certificate propagation are external waits; check their actual status rather than launching more builds.

The earlier stop guard only covers Claude turn endings. A timeout mechanism across every agent is not implemented by this guide. Give an agent this instruction when handing work back:

Report the exact build/PR/deploy and its current state. Bound each wait to at most two hours and arrange a supported wake-up. On timeout, inspect the real state and report the blocker. Do not claim that a skipped check, uploaded draft, or debug sign-in proves the Play release works.

This is a private operator guide, kept in the repository rather than the public app. It makes no Cloud, GitHub, or Play changes automatically. Progress is a checklist you control, not a live verification of those accounts.
