# Yama (Yet Another Magic App): architecture proposal

A private Magic app for Bryan and friends, on phone (iOS and Android) and in the browser. It does two jobs on one account:

- **Play:** Commander online against friends or AI, with every game stored and replayable.
- **Companion:** what Mythic Tools does today (life counter, playgroups and stats, card scanner, collection, prices, card lookup and decks), plus links to Play that Mythic Tools can't offer.

Status: proposal written 2026-10-17; building started 2026-10-18. See README.md for what works today. Repo and app-store facts below were checked on 2026-10-17.

**Changed 2026-10-18:** the database is SQLite (WAL mode), not Postgres. At friend-group scale one file next to one server process is simpler to run and back up (e.g. Litestream to object storage), and this machine has no Docker. The schema avoids Postgres-only features, so moving later is a migration, not a rewrite.

## 1. What we're building

| Area | Features | Matches Mythic Tools | Beyond Mythic Tools |
|---|---|---|---|
| **Play** | Online Commander (2 to 4 players), AI seats, lobby and invites, replays | n/a | The whole area |
| **Table** (life counter) | Life, poison, commander damage, monarch, initiative, day/night, energy and other counters, turn timer and chess clock, themes | ✓ | Every phone at the table joins one shared game by QR code. Works offline. |
| **Playgroups and stats** | Friends, guest players with no account, game log, win rates by deck, player and commander | ✓ | In-person and online games feed the same stats |
| **Scanner** | Camera scanning straight into the collection, with set, finish and condition | ✓ | Open model, runs on the phone |
| **Collection** | Containers (binders, decks, lists, boxes), condition, finish, language, purchase price, bulk edit, CSV import and export | ✓ | Imports Mythic Tools CSV losslessly. Shows owned/needed for each deck, spares and proxies. |
| **Prices** | Daily market prices from Scryfall (TCGplayer, Cardmarket), with history | ✓ | Dated snapshots kept, never shown as $0 when missing (same rules as `commander-decks`) |
| **Cards** | Scryfall-style search, Oracle text, rulings, legality | ✓ | Works offline |
| **Decks** | Deck list, folders, precons, coverage check, playtesting | ✓ | Test a deck against AI with the real rules engine (Play). |

Getting off Mythic Tools has to be painless. Mythic Tools has no API, but its CSV export (`commander-decks/data/collection/mythic-tools-export-*.csv`) has everything we need: Scryfall ID, set, collector number, quantity, condition, finish, language, altered/signed/misprint/proxy flags, container type and name, and purchase price. Import should map every column and make no guesses.

## 2. Apps and code layout

**One React and TypeScript codebase for web and mobile, with Capacitor wrapping it as the iOS and Android apps.**

Why not the alternatives:

- **React Native or Expo** gives better native camera access. But the game board we want to reuse from phase is React DOM (Tailwind, Framer Motion). We would end up writing the UI twice.
- **Tauri mobile** is what phase uses for Android. Its plugin ecosystem (camera, Google sign-in, offline database, push) is thinner than Capacitor's.
- **PWA only** can't get offline storage or the camera reliably enough on iOS for a scanner and life counter people rely on.

Capacitor lets us drop to native code where the web view is too slow. The scanner is the one likely place (section 6).

```
yama/
  apps/web/            React + Vite: the whole UI
  apps/mobile/         Capacitor shell: same build + native plugins (camera, SQLite, Google sign-in, haptics, keep-awake)
  packages/core/       TS domain logic: life counter state machine, collection ops, deck validation, search query parser
  packages/api/        TS types generated from the Rust server (tsify / OpenAPI)
  packages/board/      Game board, forked from phase's client
  server/              Rust workspace: api, game-host, jobs (card data, prices, scanner catalog)
  engine/              phase-rs fork (git submodule), pinned
  scanner/             Model, catalog build pipeline, eval set of our own card photos
```

**Distribution to friends without a public store listing:**

- **iOS:** TestFlight. This needs the Apple Developer Program ($99/yr). External testers need a one-time beta review.
- **Android:** a direct APK, or Play internal testing.
- **Web:** everything works in the browser too.

Keeping Yama out of the public stores also keeps it private, which matters for the legal side (section 11).

## 3. Rules engine (Play)

Unchanged from the first draft. Build on **[phase-rs](https://github.com/phase-rs/phase)** (MIT or Apache-2.0). It's a Rust engine that compiles to WASM, with a React client.

- It supports 92.5% of Commander cards: 30,494 of 32,950.
- It has replays as seed plus action log, reconnect, spectators, and both heuristic and LLM AI seats.
- Our two full 100-card lists each have one card it can't run yet: **Negative Zone Portal** (Fantastic Four) and **Combat Celebrant** (Riders of Rohan).

The alternatives:

- **Forge** (GPL-3.0, Java): the best AI and coverage, but a desktop app.
- **XMage** (MIT, Java): self-hostable, but a desktop client and a weak AI.
- **manabrew** (AGPL-3.0): a Rust port of Forge, still early.
- **Writing our own:** years of work before it can run real decks.

Put the engine behind a `RulesEngine` trait (new game, legal actions, apply, per-player view) so it can be swapped later.

Where our own rules work goes:

- Implementing the cards our decks need and sending them upstream.
- Our own multiplayer AI (section 7).
- House rules.

## 4. Backend

```
 Phone app (Capacitor)  ─┐                ┌─────────────────────────────────────────────┐
 Browser                ─┼── HTTPS ──────▶│ Rust server (Axum, Tokio, sqlx)             │
                         └── WebSocket ──▶│  api:       auth, users, playgroups, decks, │
                                          │             collection, sync, search        │
                                          │  game-host: live online games (one task     │
                                          │             each) and live table rooms      │
                                          │  jobs:      Scryfall bulk import (weekly),  │
                                          │             price snapshot (daily),         │
                                          │             scanner catalog rebuild (per set)│
                                          └───────────────┬─────────────────────────────┘
                                                          │
                       SQLite ─ users, playgroups, games, events, decks, collection, cards, prices
                       Object storage (R2/S3) ─ scanner model + catalog, replay snapshots, CSV exports
                       Scryfall image CDN ─ card images (cached on device, never re-hosted)
```

- **One Rust server and one SQLite database.** At friend-group scale this runs on one Fly.io machine or a small VM.
- **Game state:** live games and table rooms sit in memory and are rebuilt from the event log after a restart.
- **Auth:** Google OIDC with an invite allowlist, or (with `YAMA_OPEN_SIGNUP=1`, 2026-10-20) open to any Google account with a verified email; see "Open sign-up" under Milestones. Native Google sign-in on mobile; the server checks the ID token and issues our own session token. Password accounts (argon2id) are created only from the server's command line (`yama-server user add`), for debugging, test players, or when Google is unavailable; no route creates one, and `YAMA_PASSWORD_LOGIN=0` turns password sign-in off. The email-only dev login works only when the server listens on localhost. Admins can disable an account.
- **Play is server-authoritative.** The server sends each seat only what that seat may see, which protects hidden information. Clients send `{expected_revision, action}`. The server checks the action against the engine's legal list, applies it, appends the event and broadcasts filtered views. Details are in the first draft and carry over unchanged.

## 5. Offline-first data (Table, Collection, Cards)

Game night has bad wifi, so the companion features must work without a connection.

- **Local store:** SQLite on mobile (Capacitor SQLite plugin) and IndexedDB on web, behind one TS repository interface in `packages/core`.
- **Writes are operations, not overwrites.** Each change is an op with a client-generated UUID, such as `{op_id, entity, kind: "adjust_qty", delta: +1, at}`. Ops queue locally and sync when online. The server applies each op once, so retries are safe. Quantity deltas merge cleanly when two devices edit the same card. Plain fields (condition, container) use last-writer-wins.
- **Offline card data:** a compact card database (Oracle text, types, color identity, legality, image URLs) ships with the app and updates with each set. Size not yet measured; it will be tens of MB. Search runs locally on it, using our own parser for the subset of Scryfall syntax we use (`t:`, `o:`, `id:`, `c:`, `cmc`, `f:`, `is:`).
- **Prices** download as a daily delta. Every price carries its date and source. A missing price stays missing (shown as "no price"); it never becomes 0.

## 6. Scanner

The proven approach is: find the card's four corners, straighten the image, turn it into an embedding (a compact numeric fingerprint), and look up the nearest match in a catalog of every printing. Optionally, OCR the collector number to break ties between printings.

- **[CollectorVision](https://github.com/HanClinto/CollectorVision)** does exactly this. ONNX models (portable neural-net files) for corner detection and 128-number embeddings, a catalog of about 108,000 printings keyed by Scryfall ID (53 MB), under 100 ms per scan on a laptop CPU, and an experimental in-browser scanner. Its catalog updates regularly ([CollectorVisionCatalog](https://github.com/HanClinto/CollectorVisionCatalog), MIT).
- **Catch:** the CollectorVision code is **AGPL-3.0**, with a commercial license available. If Yama is open source under a compatible license, we can use it directly. If Yama stays private, we either write our own pipeline (the approach isn't hard; the trained models are the valuable part) or contact the author. Decide before we use any of it.
- **Plan:**
  1. Spike in the web view with `onnxruntime-web` (WebGPU or WASM) on Bryan's iPhone. Target: under 250 ms per frame, with a live box around the card and a beep or haptic when it locks on.
  2. If that's too slow, move inference to a native Capacitor plugin: Core ML on iOS, ONNX Runtime Mobile on Android.
- **Picking the right printing:** the embedding narrows it to a few printings. Then the collector-number and set-code OCR (iOS Vision or ML Kit), the user's recent set, and a one-tap correction pick the right one. Finish (foil or etched) and condition are user toggles; foil detection from a camera is unreliable.
- **Eval set:** photograph our real cards (the October purchases are a ready-made labeled set: `data/purchases.json` lists set and collector number) and track accuracy on every model or catalog update.

## 7. AI opponents (Play)

AI seats run on the server and go through the same legal-action path as humans.

1. **Day one:** phase's heuristic and search AI.
2. **Our project:** an MCTS (Monte Carlo tree search) seat that guesses the hidden cards and simulates many games ahead, with 4-player threat assessment and deck-aware plans. We tune it by running AI-vs-AI games in bulk with our real decks, which also finds engine bugs.
3. **Opt-in Claude seat:** using phase's `phase-llm` pattern, the model picks the index of a legal option and the engine checks it again.

## 8. Table mode (life counter)

- **State:** a pure reducer in `packages/core`: `apply(tableState, event)`. Events: life ±n, poison, commander damage (source commander → player), counters, monarch and initiative, turn pass, timer ticks.
- **One device:** works fully offline. The event log goes into the sync queue as an in-person game.
- **Shared table:** one phone hosts and shows a QR code; the others join a room over the same WebSocket infrastructure. Each player updates their own totals, and everyone sees the shared state. If the server drops, the host phone keeps going and syncs later.
- **Ending a game** records the winner, the decks (from the user's deck list), turn count and length, and optionally who went first, how it was won and each player's fun rating. In-person games use the same `games` table as online ones (`mode = in_person`), so stats cover both. Results can be exported to `commander-decks/data/games.json`.

A seat's `deck_version_id` is kept only if it's a version of the seated account's own decks or, on a guest seat (no account), of the decks of the person logging the game (a deck they lent). Anything else, another person's list or a version that doesn't exist, is dropped rather than refused, so an offline phone's game still uploads, and no game points at someone else's version (2026-10-19; it was a 404 on 2026-10-18).

**Deck planner** (migration `0006_planner.sql`, `server/src/plan/`; design in `docs/planner-design.md`, file format in `docs/plan-format.md`). Every user gets the same tables on their own rows:

```
plan_meta(owner_id, revision, head_import_id, head_hash, ...)    -- head; revision is part of the bundle cache key
plan_imports(id, owner_id, content_hash, meta, via, report, document_gz)   -- the newest 10 keep their upload
plan_settings, plan_stores, plan_decks(key, source import|yama, status, commander, bracket, groups, notes)
plan_states(plan_deck_id, state, content_hash, cards, log, current)        -- lists, kept once per distinct list
plan_orders, plan_order_items, plan_swaps(ext_key, stage, role, src, got, ...), plan_key_aliases, plan_quotes
plan_inputs(seq global, op_id, kind, for_export, status), plan_reviews, plan_marks   -- taps as ops (slice 4)
api_tokens(owner_id, token_hash, scopes, expires_at, revoked_at)                  -- script keys (slice 4)
```

- An import is idempotent against the head only. The key is the SHA-256 of the exact bytes of the file's `plan` value. The same hash writes nothing; any other hash applies, even an older file.
- Rows keep their ids across imports by key. A row missing from a newer file is retired (decks are archived) and restored if it comes back. Answers and ticks are keyed by text and follow renamed keys through aliases.
- Planner rows store card names, never oracle ids. Names are resolved when the bundle is built, so a card Scryfall adds later resolves without a new import. A list's identity is its `[board, name, qty]` set.
- `GET /api/plan/bundle?rev=` returns everything the plan pages need. `rev` combines the plan revision with the finish time of the latest card or price import, so a daily price import makes phones fetch again, plus a tag for the owner, so one person's cached bundle never counts as current for another. The planner never writes `price_snapshots`. Its market price is the cheapest non-foil price among printings priced within three days of the card's newest price, given with its date and source. Only real, tournament-legal paper printings count: gold-bordered World Championship Decks and Pro Tour Collector Set cards, Collectors' Edition, 30th Anniversary Edition and oversized cards are left out by a fixed set list, because the printings table has no border, oversized or set-type column.
- Every query binds the caller's id. Cascading links use composite `(id, owner_id)` foreign keys, so the database refuses cross-owner links. `SET NULL` links are owner-checked in code.
- The pages (slice 3, read-only) live under the Decks tab: a Decks | Plans | Lab control (`web/src/components/DeckTabs.tsx`; a section is one line), `/decks/plan` and `/decks/plan/d/:key`. Every derived view (copy text, diffs, change groups and statuses, bracket builds, the proposed build, "where it came from" sentences) is pure TypeScript in `packages/core/src/plan`, imported as `@yama/core/plan`. The bundle is cached in IndexedDB as `plan:<user id>`, so the pages open offline; signing out deletes it first, because it holds prices paid. Plan files are uploaded byte for byte.
- Taps on the plan pages are ops with client-made ids (`POST /api/plan/inputs`): review answers, installed ticks, "bought it" marks and ideas. The web outbox keeps them in localStorage per user until the server has them, so answers survive no signal; a retried op is answered `duplicate`. Each op runs in its own savepoint, so a bad one is stored as rejected and never blocks the rest. Answers and marks are full records, last writer wins: the later UTC `at` (whole seconds, clamped to five minutes after arrival), then Yama over an import, then the larger op id, so the result doesn't depend on arrival order. A clear is a tombstone. "Bought it" is a claim and never becomes an order by itself.
- Ops on an imported deck (or a key that matches nothing) are for the export side. Its scripts (commander-decks' `publish.py` and `pull.py`) use a script key: `yama_pat_` plus 64 hex digits, stored hashed in `api_tokens` with the scope `plan:sync`, accepted only by the `SyncUser` extractor on `/api/plan/import`, `/api/plan/head`, `/api/plan/inbox` and `/api/plan/inbox/ack`. `CurrentUser` never accepts one (it looks tokens up in `sessions`), so a key gets 401 everywhere else, including WebSockets; keys are never admin and can't make keys. People make and revoke keys in Plans, Settings; revoking someone's invite revokes theirs. The inbox cursor (`plan_meta.pulled_through`) lives in Yama, so the repo keeps none, and `seq` is a global AUTOINCREMENT.
- Buy, Prints and Spares (slice 5) are views computed on the device from the bundle (`packages/core/src/plan/{buy,prints,spares,rules,overview}.ts`), so they work in a store with no signal. The buy list takes proposals to buy that weren't answered no and planned buys with no order, and puts each in the store with the cheapest listing that can go in a cart, from each store's newest stock check (a newer "sold out" beats an older "in stock"). Totals add only known prices and count the rest as "without a listed price", never as $0. Price flags come from the owner's dated rule sets: a price is judged by the set in force on its check date (a purchase, on its order date), against Yama's price for the listing's own printing, else the cheapest non-foil copy, else the plan's recorded benchmark, and every flag names the price it used and its date. A market price more than three days older than Yama's newest price is shown as "last priced", and the Buy page says when Yama's prices stopped updating. Spares are read from the stored lists the way commander-decks' `library.py` builds them (stock with the owner's own changes, minus now; now minus after), so a card counts as out only when its list says so; a stand-in's recorded later cut is shown as a suggestion, not applied. Installed ticks and "bought it" marks are ops (above); a marked card leaves the buy list's totals and carts but isn't an order until the plan records one.
- Two routes change no plan content, so they work on imported plans too: `PATCH /api/plan/decks/{key}` links the owner's Yama deck (a plan's order stays with its export, 409), and `POST /api/plan/decks/{key}/yama-deck` makes a Yama deck in the folder "Plans" from a stored list. It refuses lists with cards Yama doesn't know (400 with the names), and its version note names the list's content hash, so asking twice returns the same deck.

Linking a deck to a container is what powers owned/needed: each deck list is checked against the collection, so you see what's in the binder, what's in another deck, and what still has to be bought or printed. That's the job the `commander-decks` scripts do today (`docs/spares.md`, scan checks). Yama could take it over later.

### How online play ended up working

- **Engine:** phase v0.113.0 from a local fork (`../yama-phase`: one commit so it builds on stable Rust, then seven AI commits, `patches/phase/0002-0008`), wrapped by `play/` (`Engine`, `Match`). `soak` plays Bryan's decks AI-vs-AI and checks that the replay log reproduces the game.
- **Board:** we didn't fork phase's 1,400-file client. Since 2026-10-19 it follows the Night table artboards (design/screens/PlayBoard and PlayBoardPhone): opponents in turn order on their commander art, a turn strip with the stop ladder, square art tiles (a tapped tile turns its art, never its name), the hand fan and a right rail with the stack and one big button whose label says what it will do. Each decision is the engine's own option list (`AiDecisionContract`), the same list the AI chooses from, shown as plain-language buttons. Tapping a card filters the list to options for that card. The server sends each card's full-size image and rules text with every view, so any card can be read at full size (hover preview on desktop, a card sheet on phones). Every option is legal by construction, every engine decision type works from day one, and the UI can grow special cases (drag to attack, mana payment) later.
- **Smart stops:** the server passes for a person unless:
  - it's their main phase,
  - the stack holds something they could answer (land abilities alone don't count),
  - or they could cast a spell at an opponent's end step.

  A full-control switch turns this off. The board's stop ladder (2026-10-19) lets a person choose their own stops by step, on their turns and on opponents' turns; the board keeps them on the device and sends them (and full control) every time it connects, so the server matches what that device shows. Their own stops replace the main-phase and end-step rules; the stack rule, full control and every non-priority decision work as before. The server also passes for people before it sends the board after a move, so the board doesn't flash a stop that is passed a moment later.
- **Attacks and blocks (2026-10-19):** the engine's option list holds only a sample of declarations (no attack, each single attacker, everyone at one defender), so the board builds the declaration itself. A declaring seat's decision carries the engine's own lists (`valid_attacker_ids` with the targets each attacker may attack, `valid_blocker_ids` with the attackers each may block), and the board sends `attack` or `block` with the chosen pairs. The server applies it to a copy of the game through the engine's normal action path, which validates it (menace and the like) and refuses an illegal one with the reason in card names, read from that seat's view. Accepted declarations go into the replay log like any other action.
- **Seat art:** each seat in the lobby, the games list and the board carries its commander's art crop and artist (looked up by the commander's name, the first partner for "A and B"). Commanders are public, so this hides nothing. The board no longer guesses from the command zone, except for older servers.
- **Runtime:** one OS thread per live game with a 32 MiB stack, because the AI search recurses deeply. Views go out over a `watch` channel and WebSocket. The replay log and public log lines are saved after every change, and live games resume after a restart by replaying the log.
- **Card support:** the deck page and the new-game form say how many of a deck's cards the engine supports ("Online play: 97/100 cards supported") and name the rest in three groups, checking every face:
  - cards it doesn't know (left out of the game);
  - cards with an unimplemented part (phase's `card_face_has_unimplemented_parts`, the test behind its `is_card_playable`);
  - cards that "may not work fully": nothing is marked unimplemented, but the parser left warnings on the text (Combat Celebrant's swallowed exert clause) or phase's per-face coverage check (`card_face_gaps`) found a gap.

  Only cards in none of the groups count as supported. It's computed on request (`GET /api/decks/{id}/online-support`) rather than stored per version, so it follows engine upgrades. phase's coverage dashboard also runs resolver, dropped-text and subtype checks that aren't public per card; on 2026-10-19 those flagged 128 more of its 35,925 faces, none of them in Bryan's decks. On 2026-10-19 both full lists showed 99/100: Fantastic Four (Negative Zone Portal, unimplemented) and Riders of Rohan (Combat Celebrant, may not work fully).
- **Hidden information:** Yama's own view type never includes libraries or opponents' hands. phase's filtered state still names opponents' library cards internally, so never send the raw engine state to a client.

### Brackets, deck stats and exports (2026-10-19)

- **Declared and estimated brackets stay apart.** `decks.bracket` is what the owner says at the table (1-5, set in Edit deck). Estimates live in `deck_version_checks`, one row per version and source, and are always labelled "estimate, checked DATE" with their source. Chips show both side by side on the deck list, the table's seat setup and the online lobby (the lobby keeps the declared bracket from when the deck took its seat, and the estimate of the exact version seated).
- **The estimate comes from Commander Spellbook** (`POST https://backend.commanderspellbook.com/estimate-bracket`, cards by Scryfall oracle id, commander and main deck only). One call returns its bracket tag, the cards it flags (Game Changer, mass land denial, extra turn) and the combos it finds. Its tags map to brackets by Spellbook's own field: Exhibition 1, Core and Oddball 2, Powerful and Spicy 3, Ruthless 4; B means a banned card. A tag Yama doesn't know is stored as sent, logged and shown as unknown, never as banned. Combos are grouped by Spellbook's own `definitelyTwoCard` and `arguablyTwoCard`, not a recount of the cards: Spellbook leaves the commander out (it's always available) and counts a notable prerequisite as a piece. Cards Spellbook doesn't know are dropped silently on its side, so Yama lists them.
- **Saving never waits on Spellbook.** `insert_version` queues a row in the same transaction; one background worker (`server/src/deck_checks.rs`) sends one request at a time, at least 4 s apart (Spellbook's guideline is about 80 a minute), honours `Retry-After` on 429, and retries failures after 1 min, 5 min, 30 min, 2 h and 12 h before stopping until someone presses "Check again" (refused within 10 minutes of an answer or 1 minute of a failed try). The check view says `pending` only while a try is due or running (the page polls every 3 s then); while a failed try waits out its pause it's `retrying` with `next_try_at`, the panel shows the error and that time, and the page asks again just after it. Only a live deck's current version is checked; a version replaced before its turn waits, and an archived deck is never shown as pending and refuses "Check again". `YAMA_DECK_CHECKS=0` turns it off, since it sends deck lists to a third party; with it on, the bracket panel and the Edit deck sheet say that the list goes to Spellbook. Spellbook asks for credit and a link, which the panel gives.
- **Offline fallback:** with no estimate, the deck page shows the local Game Changer count and what it implies by the brackets' limits (none in 1 and 2, up to three in 3).
- **Deck stats** are computed in the browser from the deck view (`packages/core/src/deckStats.ts`). Land sources use Scryfall's `produced_mana` (new `cards.produced_mana`, oracle importer version 3); fetch lands count for the land types they name, and "a basic land card" for the basics in the deck. Hybrid pips count for each color. A color is flagged when it has fewer than one land source per three pips. While any land in the deck has no `produced_mana` yet, sources aren't counted at all (a missing count, not a zero) and nothing is flagged.
- **Exports** (`packages/core/src/deckExport.ts`): names only under Commander and Deck headings (the commander-decks EDHbots lists), Moxfield with the set and number of your own copy (the one in the deck's container first, real before proxy), else a paper printing with its own finish (Scryfall's default if it's on paper and nonfoil, then regular sets, English, newest; `printings.digital` and `set_type` from default_cards importer version 2), so MTGO and Arena printings such as Vintage Masters never land in a paper deck, and MTG Arena (names only, front faces for double-faced cards).
- **Version history** lists every saved version; any two can be compared (added, removed and count changes, per board).

### Table and playgroup stats (2026-10-19)

- **Art behind each life panel.** The panel draws the commander's art crop (`PlayerSetup.art`, a Scryfall URL loaded at runtime) inside the player's own rotated box, under a dark radial wash that is darkest behind the number, with the mana colors kept as a 5 px strip. Art is drawn only from `cards.scryfall.io` and only when the artist is known, because Scryfall asks for the artist and copyright wherever an art crop shows: each art panel carries "Art by …, © Wizards of the Coast" along its bottom edge, and the player sheet repeats it. A knocked-out player's art keeps its colors under a heavier scrim with faded text (Scryfall's rules forbid desaturating its images); mana-color panels still go gray. A per-device switch in the table menu (`yama.table.art`) falls back to the mana colors. Measured on very bright art, the brightest pixel behind the digits still leaves the life total at 5.8:1 contrast.
- **First player.** A `set_first` table event (Roll for first, "X goes first" in the table menu, or the finish sheet if nobody said earlier) records who took the first turn; before anyone has passed it also makes it their turn. Passing the turn never records a first player: the app can't tell who pressed it, and a table that rolled real dice may just be moving the marker to the winner. Without a `set_first` the finish sheet asks, and the turn counter counts rounds from whoever held the turn at the first pass (a guess it never saves). Once someone says, rounds count from the first player. The finish body carries `first_seat` from the replayed log, so a retry sends the same value. Online games store the engine's starting player (`Match::starting_seat`, phase's `current_starting_player`) when they finish. Log a game asks too.
- **End-of-game capture.** The finish event carries an optional `winCondition` (combat, commander damage, combo, alternate win, mill, poison, concession, other) and optional fun ratings 1-5 per seat; Log a game asks the same. Both are optional and missing means not recorded, never a default. "Knock out" asks who did it, which fills `eliminated_by_seat`. The server checks a finish against the game's stored seats and the allowed values, refuses start and end times that aren't RFC 3339, and setting the same values again changes nothing. Log a game asks for the winner or "It was a draw" and won't save without one (no answer isn't a draw), nor a winner on a seat left blank.
- **Who sits where.** A seat is tied to your account only when you say so: "This is me" (no playgroup) or your own row in the playgroup's list. Typing another name over your seat unties it and drops your deck, so a game you only watched isn't put on your record. A person sits once.
- **Retries.** Creating a game again with the same id is how an offline phone retries. A table game's retry must name the same players in the same seats; otherwise it's refused (409) instead of numbering the finish against the wrong seats. A logged game (a finish and no table events) is only what the form said, so saving it again stores what the form says now, which covers a Save whose answer was lost and an edit made before saving again. Online game ids are refused: only the rules engine writes those.
- **Stats are computed on request** from finished games (`server/src/stats.rs`: one load, then pure functions with unit tests). A player is their account if they have one, else their playgroup member, else the typed name. Rules: every rate carries its count; under 5 games it's faded and marked provisional; win rates sit beside the share a player would win by chance (1/N averaged over their pods); turn order uses only games with a known first player and a winner, per pod size, with playgroup.gg's 4-player figures (29.2, 25.7, 23.6, 21.5%, 284,950 games, computed 2026-10-19) shown until the group has 20 4-player games of its own; win-condition shares are of the games that say how, with the rest counted as not recorded; first out is the earliest recorded knockout turn and last out the losers still standing at the end (else the last knocked out), ties counting for everyone, each out of that player's own games with at least one recorded knockout (for last out, ones with a winner too), and players with none aren't listed; streaks are wins in a row or games without a win (draws aren't wins); average minutes skip logged games, whose start and end are the same. The page says when it was computed.
- **Results per deck version** (`GET /api/decks/{id}/results`) count finished games where the deck's owner played that version. Seats the computer played don't count (online games put the host's decks in AI seats), so a mirror match counts once. A seat keeps a deck version of its own account's decks, and a guest seat one the logger lent (section 9); a lent deck's games aren't its owner's results, because only seats where the owner played the deck count. Log a game credits the version that was current on the day played (local day), and none if the deck had no saved version yet.
- **Game export** (`GET /api/games/export.json` and `.csv`, optional `playgroup`, and the browser's IANA `tz` so each game's date is the local day it started, with that day's daylight saving; `offset` in minutes is the fallback, and the file says which zone it used in `time_zone`). Deck names, version labels and version notes appear only for the exporter's own decks; other people's seats show what the table typed (deck label and commander), since their deck pages are private. JSON format `yama-games/1`: a top-level `games` list as commander-decks' `data/games.json` expects, each game leading with that README's fields (date, deck, version, player_count, result, notes) from the exporting player's seat, then the whole game with every seat. CSV: one row per seat, with spreadsheet formulas in names, notes and times defused.

### Release calendar and What's new (2026-10-19)

- **Upcoming sets** come from Scryfall's `/sets` (every set in one list, about 630 KB; `has_more` pages are followed 100 ms apart). Yama keeps sets releasing on or after the day before today, every watched set, and the sets under a watched set (`parent_set_code`: Star Trek Commander, `trc`, sits under Star Trek, `trk`; both release 2026-11-13 per Scryfall on 2026-10-19). `card_count` is what Scryfall has so far, shown as "41 cards on Scryfall so far"; a total is shown only when Scryfall gives `printed_size`, which upcoming sets don't, so there's no made-up progress bar. The Cards page asks with the reader's local date, so "out today" and "in 25 days" follow their day; the server holds that date to within a day of its UTC date (every zone's local date is), so an old date can't show past sets that are only kept for someone else's watch. Tokens, promos, one-card bonus sheets and digital sets sit behind "Show N more" unless watched directly or holding precons.
- **Watching** is per person (`calendar_watches`); PUT and DELETE `/api/calendar/watch/{code}` are idempotent. Watching a set covers the sets under it. Only a set the calendar shows the person can be watched: one releasing from the day before today (server UTC) on, or one they already watch directly or through the set above. A past set kept for someone else's watch answers 404 like an unknown code.
- **Precon lists** come from MTGJSON (MIT). `DeckList.json` (about 70 KB compressed) names every preconstructed deck MTGJSON has a list for, by set code and release date; Yama keeps the `Commander Deck` entries (198 on 2026-10-19). A Collector's Edition (16 of them then: 40K, M3C, FIC and MSC have one per deck) is the base deck in other printings, so it's stored with `variant_of` naming its base (same set, and the file name without `CollectorSEdition` or the deck name without "Collector's Edition") and shown under that deck as "Collector's Edition: start from its list"; counts are of decks, not files. A deck the index stops naming (renamed or withdrawn, common in preview season) is deleted at the next good refresh; an index with no Commander decks at all is logged as a failed run and deletes nothing. A deck's own file (`decks/<fileName>.json`, about 540 KB of full card data) is downloaded only for watched sets (by the daily pass, at most 16 a pass, one a second; again after 7 days in case Wizards corrects a list, until 28 days after the deck's release; Collector's Editions only once someone has started one) or when someone presses "Start a deck" (`GET /api/precons/{file_name}`, which only serves decks from MTGJSON's own index and won't ask again within a minute of a failed download). It's kept as a pasteable list: Commander and Deck sections, one `1 Name (SET) 123` line per printing; tokens, planes and schemes are left out. Names are Scryfall's: MTGJSON writes every multi-face card "Front // Back", which is Scryfall's name too except for meld cards (Gisela, the Broken Blade) and reversible cards (Sol Ring // Sol Ring is Sol Ring); for those two layouts the list uses MTGJSON's `faceName`. Checked against all 198 Commander deck files in MTGJSON 5.3.0+20261018: these were the only names Yama's card data didn't match (three Secret Lair decks, including all four of their commanders).
- **"These precons are out"**: once a watched set's lists are in MTGJSON's index, the Cards page names each deck, its commander once the list is downloaded, and MTGJSON's source (usually Wizards' decklist article), with "Start a deck". That opens Add a deck pre-filled with the name and stock list for the person to check and save, through the normal deck import, so nothing is created behind their back. Cards Yama's card data doesn't match are listed before saving (brand-new cards arrive with the weekly oracle import; anything else is a name to check). A deck with the same name, or the name of its Collector's Edition, shows as "In your decks", and Add a deck warns before making a second deck with a name already in use. After the save the new deck replaces the `?precon=` page in history, so Back doesn't reopen the filled-in sheet. The card leads the Cards page until the set has been out for 28 days, or is out and the person has a deck for every list; then it folds into a closed "Star Trek Commander precons" section below the calendar, and the watch stays.
- **Refresh**: with `YAMA_AUTO_IMPORT=1` a background task wakes hourly and refreshes each source once it's 20 hours old, waiting 55 minutes after a failure; `yama-server import-calendar` runs everything once. Runs are logged in `import_runs` (kinds `scryfall_sets`, `mtgjson_decklist`; for MTGJSON `source_updated_at` holds its build date), and the page shows when each was last checked and whether the latest try failed. Without auto import the page says it hasn't checked, rather than showing an empty calendar as if nothing were coming.
- **What's new** (`web/src/whatsNew.ts`, page at `/new`) lists shipped features newest first in plain sentences, ending with the unofficial-fan-software notice and data credits. Each device remembers the newest entry it has seen (`yama.whatsNew.seen`) and shows a one-line notice above every page until then: "N updates since you last looked" once it has a seen entry, and "Yama keeps a list of what's new" on a device that has never opened the page. Add an entry when something people will notice ships.

### Simulation lab (2026-10-19)

Bryan wants to know how the Commander precons do against each other, and to test his own deck changes. The design and analysis live in commander-decks (`docs/deck-lab-plan.md`, `scripts/sim/`); Yama plays the games and shows the results.

- **Core:** `play/src/lab.rs` plays one all-AI game from a schedule line (`GameSpec`) and returns its result line (`GameResult`). It covers the turn, action and per-turn loop caps, the per-thread CPU-time cap, and panic isolation on a named 32 MiB thread. A watchdog can write off a hung game from what the game last published (`Live`). The JSON-lines schedule and result formats are the contract with the Python analysis. A result line for a given schedule line must not change under a refactor (apart from `ms`, and `runner`, which names the build).
- **Batch runner:** `play/src/bin/lab.rs` is a thin CLI over the core. It adds threads, resume (`--skip-done`), the hang watchdog with clean restarts, and deck loading. It runs on the Mac and on saget (`deploy/lab.sh`).
- **Tables** (migration 0007):
  - `precons` is the global catalog, imported from commander-decks' `data/sim/decks/index.json` with `yama-server import-precons`. Precons that repeat an earlier list are left out of that index (Bryan, 2026-10-19), so they're never imported.
  - `lab_runs` and `lab_ratings` hold analysed runs (`summary.json` from `analyze.py`), imported with `yama-server import-lab`. A run with no owner is global; a run with an owner is visible to that owner only. A global run may only rate precons: the import refuses a summary that names any other deck (in its ratings, matrix or paired comparison) unless it has an owner, and precon matchups only list catalog precons. Each rating's `extra` keeps the deck's whole summary entry, and the run keeps its whole summary, so analyze.py's simulation confidence (a per-deck `confidence` with a level and reasons, and the run's `confidence` block) needs no column of its own.
  - `lab_experiments` and `lab_experiment_games` are for "Try a change" (below): a user's own paired runs, played by the server on the core, one row per scheduled game so a restart resumes.
- **APIs:** `GET /api/precons` (the latest global precon-ratings run joined in), `GET /api/precons/{id}` (list, rating, 1v1 matchups from the run's matrix), `POST /api/precons/{id}/deck` (a Yama deck from the stock list, idempotent with `op_id`; the op record and the deck commit in one transaction), `GET /api/lab/runs` and `GET /api/lab/runs/{id}` (global and own; anyone else's is a 404). The release calendar's MTGJSON precon lists are a different thing and live at `GET /api/calendar/precons/{file_name}`. A paired run (one of Bryan's batch runs, imported with `--owner`) also comes with `paired`: each list's win rate with its Wilson interval, and each comparison named, with analyze.py's bootstrap interval and a verdict worded as "Try a change" words it. Every rating also carries `confidence` (`{level: ok|doubtful|unreliable, reasons}`, read leniently: a level this build doesn't know reads as doubtful), every run label the run's `confidence` block (counts per level, the method in the analysis's words, the reference run), and every paired list the confidence of its rating in the same run.
- **Try a change** (`server/src/lab/`): a user's own paired experiment, played inside the server.
  - `POST /api/lab/experiments` takes a base (one of your deck versions or decks, a precon, or a pasted list), a change (a whole list, or cards to add and cut), a field (all precons, the strongest n or the n nearest in strength in the newest global rating run, chosen precons, or your own decks), games and an AI level (Easy by default). Both lists must resolve in Yama and in the engine (unknown names come back per list), have 100 cards and a valid commander. Other deck-check findings (colour identity, singleton, bans) are warnings: it is a simulation. The field needs 3 decks. Lists and opponents are frozen into the experiment's spec when it is created.
  - Paired design (`pairing.rs`): games = 2 x pods. Pod t has three field decks, picked least-used first with a seeded tie-break and seated to balance seats, the tested list in seat t % 4 (seat 0 goes first, as in the batch runner), and a seed. The base and the changed list each play that exact pod and seed, as adjacent games, so a part-played experiment stays paired. Limits are schedule.py's 4-player defaults (120 turns, 200,000 actions, 600 CPU seconds) plus the core's loop guard.
  - Limits: anyone but an admin gets 100, 200 or 400 games, Easy or Medium, and one experiment playing plus two waiting (409 beyond, checked before anything is built). Admins: any even number up to 2,000, any level, no queue limit. `op_id` makes a retried create return the first experiment.
  - Sizes are checked before any expensive work, so one small request can't exhaust memory or CPU: a body of at most 256 KB (413), and per list at most 64 KB of pasted text, 300 card lines, 100 copies on a line and 250 cards, with at most 200 cards to add and cut (400s that name the list). The engine is only asked which names it knows, one lookup per line; it never expands quantities while checking. A deck in a field of your own decks that can't be simulated isn't sent to it at all. Merging repeated lines is linear.
  - Worker (`worker.rs`): YAMA_LAB_THREADS game threads (default 2; 0 = no new experiments) with 32 MiB stacks, on the play hub's already-loaded engine. First in, first out by experiment across users; a non-admin's next experiment waits for their current one. Each result line is stored with the experiment's progress and summary in one transaction, only where no result is stored yet. Unplayed games are played on the next pass, so after a restart queued and running experiments resume, replaying only games that were in flight. Games play under the limits frozen into the experiment. Every start is counted (`attempts`): a stack overflow or abort inside a game ends the whole server, which nothing can catch, so a game started twice without a result is written off as an error instead of crashing the server on every restart. A game with no move for 300 s is written off as an error. Its thread can't be stopped, so it keeps its place: the lab plays one game fewer at a time until that thread ends or the server restarts. Cancel stops new games; running ones finish and count. Cancel recounts in the same immediate transaction as its status change, so it serialises with a result being stored. A cancelled experiment's summary is marked final only when none of its games is playing: at once when none is, otherwise when the worker stores the last one, and at startup for any a stopped server left open. A game is claimed in memory before the write that starts it, and that write skips experiments no longer queued or running, so no game can start after a cancel has found nothing playing. Delete removes the experiment and its games.
  - Builds: every game plays on the server's current build (engine, card data, runner) and its result line says so. A deploy or a card-data refresh part way through doesn't split a pod: a pod with one game stored from another build has that game cleared and both games replay on this build (checked once per experiment per process). Pods split anyway (stored before this rule) are left out of the paired difference and counted as `split_builds`. The summary lists every build with its games, and the experiment's label (engine, card data, runner) comes from the result lines, naming every build used; before the first game it shows the build the experiment was created on.
  - Summary (`stats.rs`), scored as analyze.py does (time caps, panics and errors unscored; turn and action caps count as no winner): each list's win rate with a Wilson 90% interval and average place, and the paired difference over pods where both games were scored, with the Agresti-Min 90% interval for matched pairs. That interval is closed-form rather than a bootstrap: the same results always give the same interval, it keeps a sensible width when few pods differ, and it agrees with analyze.py's bootstrap over templates to about a point at these sizes. The verdict reads "Probably better (+4 points, 90% interval +1 to +7)", "Probably worse (...)" or "Can't tell yet: run more games" (also with fewer than 10 paired pods). It goes by the interval as shown in whole points: better only when the low end reads +1 or more, worse only when the high end reads −1 or less, so the words never sit beside an interval that reaches 0. Progress has an ETA from the lab's recent pace: in whole minutes for admins, rounded up to 5 minutes for anyone else. The exact number of games queued ahead (anyone's) is shown to admins only, since it would tell other users about each other's experiments; the rounding keeps an ETA, the expected times and your own pending games from being combined into that number (an ETA still shows roughly how long the queue is).
  - `GET /api/lab/experiments` (own, newest first), `GET /api/lab/experiments/{id}`, `GET /api/lab/experiments/{id}/pods` (every pod with its seats and both lists' games: how each ended, the tested list's place, turns, seconds), `POST /api/lab/experiments/{id}/cancel`, `DELETE /api/lab/experiments/{id}`; anyone else's is a 404. Without the engine card data every experiment endpoint returns 503 "Simulations need the engine card data on this server".

The pace behind it is seconds per game: from games finished in the last hour, else the mean length of the latest experiments' games spread over the threads. It counts everyone's games, so only admins get it exactly (seconds per game, its basis and sample, times in whole minutes); anyone else gets the times rounded up to 5 minutes, like their ETAs. The recent pace only counts games finished in the last hour, so a resumed experiment's older games don't slow the estimate (or the ETA).

### Open sign-up (2026-10-20)

Bryan (2026-10-20): "we can also open up signups to anybody. I don't really care as long as it's secure with Gmail, that is, not with the username/password." Built behind `YAMA_OPEN_SIGNUP=1`, off by default, so nothing changes until it is set. Operating steps (publishing the Google consent screen, `YAMA_TRUSTED_PROXIES`) are in deploy/README.md.

- **Who gets in** (`server/src/auth.rs`): a Google ID token signed by Google (RS256 only, keys from Google's JWKS) for one of our client IDs, with `iss`, `aud`, `exp` and `sub` all required (jsonwebtoken only insists on `exp` by default, and skips the issuer and audience checks for a token that lacks them) and `email_verified` true (the old string form "true" is read too). With the flag off the email must be an admin's or invited, as before. With it on, anyone may make an account. An account is tied to its Google `sub` on first sign-in: a different Google account with the same email is refused (a recreated non-Gmail account can't take over), the same `sub` under a new email is the same account, and open sign-up never gives a Google sign-in an existing account that was made another way (password, Cloudflare Access, dev login) unless that email is invited. Unknown key ids refetch Google's keys at most once a minute. Cloudflare Access is unchanged (its policy is the invite list); its tokens now must carry `exp`, `iss` and `aud` too.
- **Limited accounts:** `User::limited` is computed on every request, not stored: a Google-linked account that isn't an admin, has no command-line password and isn't on the invite list (`auth::limited_sql!`). So inviting someone lifts the limits at once, withdrawing an invite applies them, and accounts made by Cloudflare Access, dev login or `user add` are never limited. While the flag is off, a limited account's sessions and script keys are refused (`may_use_yama`), so turning open sign-up off shuts out everyone who came in through it without touching their data.
- **Disabled accounts:** `users.disabled_at` (migration 0009), set by `yama-server user disable EMAIL` or an admin in Group, You, Accounts (`/api/admin/users`, `/api/admin/users/{id}/disable|enable`; not yourself, and another admin only from the command line). Disabling deletes the sessions; every sign-in path, `CurrentUser`, script keys and Cloudflare Access refuse the account; the lab worker skips its experiments until it is enabled. Open WebSockets (a live online game, a shared table) aren't cut; they end at the next reconnect.
- **Rate limits** (`server/src/limits.rs`, in memory, per process; per-account ones skip admins): sign-in 10 tries per 10 minutes per client address and per email (Google and password together, checked before any token or password work); card search 120 a minute and name lookups 300 a minute; the offline card bundle 10 an hour; join codes for playgroups and online games 20 per 10 minutes; Mythic CSV and plan imports 60 an hour; deck creates, saves and parse previews 120 per 10 minutes; new online games 30 an hour. A refusal is a 429 with `Retry-After`.
- **Client address:** the TCP peer (axum `ConnectInfo`), unless the peer is in `YAMA_TRUSTED_PROXIES`, in which case Cloudflare's `CF-Connecting-IP`. Cloudflare sets that header and overwrites any value a visitor sends, so it is the visitor's address only when the request came through the tunnel; on saget the tunnel connector reaches Yama over the `novalyst_default` Docker network, so that network's range is the list. LAN requests (Docker hands over the LAN client's own address on port 8099) and anything else outside the list keep the peer and ignore the header. IPv6 addresses count by their /64. With no list, all tunnel traffic counts as one address and the first such request logs a warning.
- **Shared resources:** the lab (`lab/experiments.rs`): limited accounts get 100-game experiments, one at a time, and `YAMA_LAB_OPEN_DAILY_GAMES` (300) games per 24 hours, counted from `lab_usage` (one row per experiment, kept when the experiment is deleted, so deleting runs doesn't reset the day). Games waiting or playing are capped for everyone but admins together (`YAMA_LAB_QUEUE_GAMES`, 2,000) and for limited accounts together (`YAMA_LAB_OPEN_QUEUE_GAMES`, 400). All checks run before anything is built and again inside the transaction that stores the experiment. `/api/lab/pace` returns `game_choices` and the `allowance`, and "Try a change" offers only those sizes. Online play: at most 10 unfinished hosted games for anyone but an admin, 2 for a limited account and 20 for all limited accounts together, since each live game holds a thread and its match. Commander Spellbook: at most 20 checks an hour per deck owner (the rest wait their turn; the worker's global pace of one request per 4 s is unchanged). Imports: Mythic CSV up to 4 MB (1 MB limited), plan files up to 8 MB (2 MB limited). Shared tables: 4 hosted at once per account, and a 16-snapshot backlog per room instead of 64. Card searches longer than 1,000 characters are refused.
- **Privacy:** every per-user route already binds the caller's id and answers "not found" for anyone else's row. `server/src/privacy_tests.rs` checks it end to end from a limited account's session (decks and versions, deck checks and results, collection with prices paid, containers, CSV export, logged games and the game export, playgroups without and with a join code, online games, script keys, plan imports and bundle, owned lab runs, admin routes); plans, lab experiments, search ownership and game exports also have their own tests. `server/src/signup_tests.rs` covers the token checks, open and closed sign-up, account binding, disabling, password sign-in and the sign-in limits, and checks that only `auth.rs` touches `password_hash` and only the command line calls `add_local_user`.
- **UI:** the sign-in page says "Anyone with a Google account can join. Yama is free, unofficial and private to its users." when sign-up is open, instead of "Yama is invite-only", and keeps the unofficial notice. In the admin area (`/admin`, People; it was Group, You until 2026-10-22), admins see "Who can sign in" explain that an invite now means the full allowance, and the accounts list (newest first, with how each came in and Disable, Enable, Invite and Delete).

#### OAuth sign-in for the tools (slice 3, 2026-10-22)

Bryan wanted Claude to connect without pasting a key, from Claude Code and from claude.ai's connectors (`server/src/oauth/`, migration 0018, `web/src/oauth/`).

- **Discovery:** `/mcp`'s 401 carries `WWW-Authenticate: Bearer resource_metadata="<base>/.well-known/oauth-protected-resource/mcp", scope="mcp"` (plus `error="invalid_token"` when a token came). The protected resource metadata (RFC 9728, also at the root path) names `<base>/mcp` and the issuer `<base>`; the authorization server metadata (RFC 8414) lists the endpoints, `code` only, `authorization_code` and `refresh_token`, S256 only, `none`/`client_secret_basic`/`client_secret_post`, scopes `mcp` and `offline_access`, and `authorization_response_iss_parameter_supported`. `<base>` is `YAMA_PUBLIC_URL`, never the Host header; without it every OAuth route is a 404 and the challenge is a bare `Bearer`. No Client ID Metadata Documents: fetching a URL a client names is a server-side request we don't need, and without the flag Claude registers through DCR.
- **Registration** (RFC 7591, `POST /oauth/register`): redirect URIs must be loopback (`http://localhost`, `127.0.0.1`, `[::1]`, any port) or https on `YAMA_OAUTH_REDIRECT_HOSTS` (claude.ai and claude.com by default), else `invalid_redirect_uri`; an open https redirect would let anyone collect a Yama grant with a link (`oauth/redirect.rs`). Claude registers as a public client (`none`); RFC 7591's default `client_secret_basic` gets a secret, stored hashed. Names are the app's claim: hidden characters stripped, 80 characters, shown only as text. 30 an hour per address, 500 waiting for a first sign-in, 5,000 in all; ones never used are swept after a day, ones with no connection left after 30 days.
- **Consent:** `/oauth/authorize` is a page of the web app outside the shell (the normal sign-in first; the address is kept). It asks `GET /api/oauth/authorize?…` to check the client, the redirect URI (exact, or loopback with any port and loopback host), `response_type=code`, an S256 challenge, the scope, `state` and `resource`. A bad client or redirect URI is an error on Yama's page, never a redirect; the app's other mistakes go back to it (`error`, `state`, `iss`). The page shows the app's name, where it sends you back (loopback says "a program on this computer"), the account, what the tools allow (read, and suggest changes that wait for the person's Apply) and a caution. Allow and Deny `POST /api/oauth/authorize` with the session (Origin must be `<base>`); the answer is the redirect with `code`, `state` and `iss` (RFC 9207) or `error=access_denied`. Refused while an admin views as someone (the view guard refuses the POST before routing, and the check refuses the GET itself), and for accounts `may_use_yama` rejects.
- **Codes:** random, SHA-256 in `oauth_codes`, single use, 2 minutes, bound to the client, the exact redirect URI, the challenge, the account, the scope and the resource. A failed exchange (wrong verifier, redirect or client) leaves the code alone; a second exchange of a used code revokes the grant it made.
- **Tokens** (`POST /oauth/token`, form-encoded, `no-store`, RFC 6749 errors): `yama_oat_` access tokens (1 hour) and `yama_ort_` refresh tokens (30 days), stored hashed in `oauth_tokens` under a grant (`oauth_grants`: account, client, scope, resource, created, last used, revoked and why). Exchanging a code replaces the account's earlier grant for the same client. Refresh tokens rotate; a used one presented again revokes the grant, except within 10 seconds of its first use (two refreshes racing after a 401). `resource`, when sent, must be `<base>/mcp` in canonical form. `POST /oauth/revoke` (RFC 7009) revokes the token's grant if it's the caller's.
- **Where tokens work:** `mcp::caller` accepts a live access token (`Via::OAuth`) and resolves the account through `auth::user_by_id` (disabled and open sign-up rules), recording the grant's last use at most once a minute; tool calls go through the same tools and limits as a key. `CurrentUser` refuses any `yama_oat_`/`yama_ort_` bearer outright, without falling back to the cookie, so every other route is a 401.
- **Connected apps** (Decks, Plans, Settings, "Connect Claude"): the Claude Code command and the claude.ai steps, then each live grant (name, kind, connected, last used) with Disconnect, which revokes it. Script keys stay below. Hidden while an admin views as the person. Withdrawing an invite or deleting the account ends its connections (`admin/delete.rs` deletes grants, their tokens and codes); a disabled account's tokens are refused while it stays disabled.
- **Logs:** ids and outcomes (registered, approved, denied, connected, revoked and why, replay or reuse warnings), never a token, code, verifier or secret.

### A deck's cards in the collection, and Mythic re-imports (2026-10-23)

Bryan (2026-10-23): "there should be an option to add all the cards from a deck you imported to your collection". His collection came from a Mythic Tools export of his bulk boxes only, so his decks showed 13 to 33 of 100 cards as owned; and a newer Mythic export added every row again. Both are fixed for everyone (`server/src/collection/deck_box.rs`, `server/src/collection/mythic.rs`, migration 0021). Server-planned bulk changes are applied as ordinary collection ops in one transaction; their ids carry the count of the owner's applied ops (`collection::op_stamp`), so a retried request applies once and a later run after any change gets fresh ids.

- **Add to my collection** (deck page button; the deck import offers it after saving, `/decks/{id}?collect=1`; `GET`/`POST /api/decks/{id}/collect`; `yama-server collection add-deck`). The target is a state: the deck's box holds its list (commander and main deck, not the sideboard). The box is the container `decks.container_id` links, or a new `deck` container named after the deck (" (2)" when another live deck has a box by that name), then linked. Each missing card is added in the printing `deck_prints` names, else `decks::collection_printing` (paper, not a promo or gold-bordered or other side product, nonfoil, Scryfall's default, English, newest). A card the deck marks as a proxy (`deck_prints.proxy`, from a CSV's Proxy column or an Archidekt "Proxy" category) is added as a proxy. Copies of exactly that printing, finish and proxy-ness outside deck boxes can be moved in (the web's default), left with new copies added, or left with the card left out; a container of kind `deck`, or any container a live deck links, is never a source. The deck's list is never changed and nothing re-syncs it from the box. The preview says how many copies the box holds that the list no longer has; adding never removes them. The command line leaves same-printing copies where they are unless `--move-same-printing`, because a box imported from elsewhere may hold other physical copies.
- **Mythic Tools re-imports count copies.** A copy kind is printing, finish, language and proxy (condition is noisy between scans; altered, signed and misprint are rare and don't count either). F is the file's total of a kind, Y Yama's total across every container and unfiled. F > Y adds F − Y to the containers the file names, where the file has more than Yama, matching Yama's copies to the file's rows by condition first. F ≤ Y adds nothing, so copies moved in Yama (into a deck box) stay put. Copies in a container the file names beyond what the file lists there are "no longer in this export": shown, and removed only with the checkbox or `--remove-missing`, before adds, so a move between two named containers follows. Unfiled copies and containers the file doesn't name are never touched. The same file again adds nothing (`mythic_imports` by SHA-256, and the old `mythic:<hash>:<row>` op ids for files from before). A container Mythic retyped (Bryan's "bulk" was a list on 2026-10-09 and a box by 10-18) is the same container when Yama has one of that name in another type (decks excepted); it takes the file's type. The web shows a dry run (`?dry_run=1`) before importing; `yama-server import-mythic` does the same.
- **Deck containers in a Mythic file** still make or update decks (`decks::sync_deck_from_container`), which now keeps the deck's existing commanders while they're in the container, so a deck with several legends no longer loses the one its owner picked. Only decks the sync made (folder "Mythic Tools") follow their container: a deck made another way whose box the file names (imported on the web, then "Add to my collection") keeps its list, since the box can hold more than the list.
- **Command line for fixing someone's decks:** `import-decks DIR --update` makes a file whose name matches a live deck (any case) a new version of it, read and saved with its printings the way the web import does (`deck_import::read_list`), and adds no version when the cards are the same. Without `--update` a name a live deck already has exactly is skipped, as before. `deck archive` and `deck rename` match names in any case and refuse a name two live decks share.

### Forge as a second Lab engine (2026-10-22)

Bryan (2026-10-22): "we also need to allow more engines for running rules. Maybe support Forge too." Every Lab run (Try a change, as is, Compare decks, head to head) now picks its engines: phase (the default), Forge, or both side by side.

- **Separate program, separate container.** Forge (GPL-3.0) runs as its own program in `yama-forge` (deploy/Dockerfile.forge-worker), one JVM per game, through the deck lab's batch runner (`forge-worker/forge_runner.py`, a copy of commander-decks `scripts/sim/forge_runner.py`) behind a small HTTP front (`forge-worker/worker.py`). No Forge code is in Yama. Yama calls the worker, never the other way round, on an internal Docker network (`yama_forge`, no internet) with a shared secret (`x-forge-secret`); the worker publishes no port.
- **Games and engines** (`server/src/lab/forge.rs`, migration 0017): every scheduled game names its engine (`lab_experiment_games.engine`). The lab threads play phase games only; `LabWorker::run_forge` hands Forge games to the worker up to the slots it reports, oldest run first, one run at a time per person. Forge games get Forge's wall-clock limit (900 s). A "both" run has each pod twice, its Forge copies after every phase game (ids `…-f`, an even ord offset, so pods stay paired in both halves); `summary` holds the phase half and `summary_forge` the Forge half, never pooled. `stats::agreement` says whether the halves agree: opposite verdicts or intervals that don't overlap are a disagreement.
- **A worker that's down:** nothing is claimed while it doesn't answer, so its games wait; the run page says "Forge worker offline". A game whose request fails goes back in the queue; after 3 failed tries it is written off as an error labelled as Forge.
- **Cards Forge doesn't know:** the worker checks names against Forge's card scripts (`/check`); Yama keeps the answers per worker version. A tested list with such cards is refused, and precons with them are left out of a Forge field (as phase's unknown cards are). `POST /api/lab/engines/check` shows both engines' gaps before a run.
- **Seeds:** Yama's seeds are 64-bit; the worker hands Forge the low 63 bits (a negative Java long reads as a flag on Forge's command line) and the result keeps Yama's seed.
- **Limits:** a Forge game counts as 2 against the daily allowance (`FORGE_WEIGHT`); a "both" run counts 1 + 2 per pod game.
- **Admin, Server** shows the worker: answering or not, engine, slots, games playing and waiting.

## 11. Risks

- **Legal and IP:**
  - Stay inside Wizards' Fan Content Policy: free, non-commercial, an "unofficial, not endorsed by Wizards" notice, no Wizards logos, and no card images or rules documents shipped. Images come from Scryfall at runtime, under its rules (read 2026-10-19 at scryfall.com/docs/api): don't cover, crop or clip the copyright or artist name on card images; don't distort, skew or stretch them; don't blur, sharpen, desaturate or color-shift them; with an art crop, show the artist name and copyright in the same interface; no paywall. The life panels scale the art crop to cover the panel without distorting it (an art crop has no artist name or copyright to cut off) and lay a separate translucent scrim over it for legibility; the image itself gets no filter.
  - Companion apps like Mythic Tools are common in the app stores. A full game client in a public store listing is a bigger target. Distributing through TestFlight and an APK keeps us private.
- **Engine maturity:** phase is seven months old, mostly from one maintainer, with about 1,559 open issues. Pin it, run AI soak tests before each upgrade, and keep the trait boundary.
- **Replay drift:** a replay only reproduces on the engine version that recorded it. Store `engine_version` and keep old WASM builds or snapshots.
- **Scanner:**
  - License (AGPL), and accuracy on foils, sleeves and bad lighting, especially when telling printings apart.
  - The eval set and one-tap correction contain this.
- **Scryfall changes:** Scryfall changed its platform three times in 2026 (JSON Lines bulk files in July, WebP images on 2026-10-14). The `small`, `large`, `border_crop` and `art_crop` JPEGs stop on 2027-01-01, so the import reads `thumb`, `grid` and `art` (falling back to the JPEG keys) and keeps the old column names. Image URLs always come from the card JSON, never from `format=image` redirects.
- **Prices:** Scryfall prices are market reference prices, not availability or checkout quotes. Label them that way. As far as I know, TCGplayer's own API is closed to new developers (not rechecked), so Scryfall is our price source.
- **Scope:** this is several apps. The milestones deliver something usable at each step; stop wherever it's good enough.
